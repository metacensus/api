# The MetaCensus API contract, in Protocol Buffers

The shape of every request and response under `/metacensus/api/v1`, defined
once in `.proto` and generated into Go and TypeScript.

**Nothing consumes this yet.** The SPA in `src/` still uses `types/*.ts`, demo's
Bun API still hand-writes its handlers, infra's Go API still uses
`core/shared/types`. This directory is the definition and its proof; adopting it
is separate work. `packages/contract` — the npm package that exports
`API_PREFIX` — is untouched and remains what the SPA imports today.

## Layout

```
contract/
  proto/   .proto sources and buf config — the definition
  go/      generated Go, the wire encoder, and the tests
  ts/      generated TypeScript interfaces
```

The three are meant to survive being moved into a repository of their own as a
directory move rather than a rewrite. The only thing that crosses a boundary is
`ts/test/golden.ts`, which imports from `ts/src` and is generated by the Go
tests — a deliberate coupling, since proving the two languages agree requires
something that sees both.

## Working on it

Everything is a make target, run from `contract/`:

```bash
make deps      # npm ci in ts/ (Go needs no install step)
make gen       # regenerate Go and TypeScript from the .proto sources
make golden    # regenerate the golden JSON and the TypeScript cross-check
make check     # everything CI runs bar the freshness diff
```

Generated code is committed. CI regenerates it and fails on any diff, so a
stale artifact cannot merge.

## Protobuf as a type system, JSON as the wire

The wire format is JSON, always. Protobuf binary is not used, not supported,
and not a fallback. Payloads stay curl-able and legible to any REST client;
protobuf is here for the schema, the code generation and the breaking-change
detection, not for the encoding.

That has consequences worth stating plainly, because they are what someone
reading a `.proto` file will otherwise get wrong:

- **Marshal with `protojson`, never `encoding/json`.** `contract/go` exports
  `Marshal`, `Unmarshal` and `MarshalOptions` so this is code rather than a
  convention. Under `encoding/json` the generated types produce enums as
  integers, timestamps as `{"seconds":…,"nanos":…}` and 64-bit integers as
  unquoted numbers — three different wrong answers.
- **This is also why `protoc-gen-go-patch` / protopatch is not used**, though
  `infra/temporal` uses it. It exists to rewrite `json:` struct tags. protojson
  does not read struct tags, so it would change nothing that matters and fix
  none of the three problems above.
- **Field names are `snake_case` in proto and `lowerCamelCase` on the wire.**
  protojson does that conversion itself and it already matches what the SPA
  sends. There are no `json_name` overrides.
- **Enum values are PascalCase** — `PendingReview`, `Statement`, `For` — because
  protojson serialises an enum as its value name, so the value names *are* the
  JSON vocabulary. Zero values are `Unspecified`.
- **Enums are nested inside the message that owns them.** Protobuf scopes enum
  value names to the enclosing message, C++ style, not to the enum, so two
  enums under one parent cannot both have an `Unspecified`. Nesting per resource
  makes collisions structurally impossible. The single exception is
  `PropConclusion`, a wrapper message that exists because `Prop` needs two
  enums; the .proto says so at the point it happens.
- **All ids are strings.** demo mints integer serials, infra mints prefixed
  UUIDs (`user:0192a642-…`). The contract cannot ratify either, so it requires
  the one representation that carries both.

## The emit decision

`protojson` has two options for how much to write, and the choice has to agree
with what ts-proto generates or the two languages disagree about which keys are
always present. The relevant difference, measured rather than assumed:

```
EmitDefaultValues   {"page":0, "limit":0}
EmitUnpopulated     {"page":0, "limit":0, "total":null}
```

Both emit zero-valued scalars, empty arrays and `Unspecified` enums. They part
company on fields that support presence — message-typed fields, proto3
`optional` scalars, oneofs — where `EmitUnpopulated` writes `null` and
`EmitDefaultValues` writes nothing.

**The contract uses `EmitDefaultValues`, paired with ts-proto's
`useOptionals=messages`.** Under that ts-proto setting a message-typed field is
generated as `created?: string | undefined`, and `null` is not assignable to
`string | undefined`. `EmitUnpopulated` would therefore emit documents the
generated TypeScript rejects — and it does: temporarily swapping the option
makes `ts/test/golden.ts` fail to compile on the first absent timestamp. The
check is real, not theoretical.

The pairing gives one rule per field kind:

| field kind                        | JSON              | TypeScript          |
| --------------------------------- | ----------------- | ------------------- |
| scalar, enum, repeated            | always present    | required            |
| message (incl. Timestamp, wrappers) | present or absent | `?: T \| undefined` |

A consequence: **presence is expressed only through message-typed fields.**
There are no proto3 `optional` scalars anywhere in the contract. They would be a
third case — omitted by the encoder, but not marked optional by ts-proto under
`useOptionals=messages` — so the two sides would disagree about whether the key
exists. Where a scalar genuinely needs to be absent, the contract uses a wrapper
message: `ListMetadata.total` is a `google.protobuf.Int32Value`, because "no
total was computed" and "the total is zero" are different answers.
`TestPresenceIsExpressedOnlyByMessageFields` enforces this.

## What the tests prove

`go test ./...` in `go/`:

- **`TestGolden`** — every message, populated, marshalled, diffed against a
  committed JSON file. This is what makes the conventions above real rather than
  aspirational: they are properties of these files, not of a paragraph.
- **`TestRoundTrip`** — every golden parses back and re-marshals identically, so
  a golden cannot be hand-edited into something the decoder rejects.
- **`TestEveryMessageHasAFixture`** — a message added without a golden fails.
- **Wire-shape tests** — lowerCamelCase keys at every depth, PascalCase enum
  strings that are real values of their enum, RFC 3339 timestamps, string ids,
  no top-level arrays, `{items, metadata}` on every list, no package-scope
  enums, no `optional` scalars.
- **`ts/test/golden.ts`** — the same documents as TypeScript literals, generated
  from the same bytes in the same run, type-checked by `tsc` against the
  generated interfaces. Its `enumWireValues` pins each enum member to the exact
  characters protojson wrote, using a `` `${Enum.Member}` `` template literal
  type: rename a value on one side only and it stops compiling.

`ts/scripts/check-no-runtime.mjs` asserts the TypeScript is genuinely types —
empty `dependencies`, and no value imports in `src/`. ts-proto's default
`forceLong` would pull in the `long` package, which is exactly the kind of
regression that would otherwise pass every other check.

## Tooling and pinning

`buf` and `protoc-gen-go` are Go 1.24 `tool` dependencies of `go/go.mod`, run
via `go tool`. No Homebrew, no `go install`, no version that can differ between
a laptop and CI. `ts-proto` is pinned in `ts/package.json` and buf invokes it as
a `local:` plugin out of `ts/node_modules/.bin`.

One consequence to know about: because `go tool` only works inside its own
module, **buf runs from `go/`, not from `proto/` where its config lives**. Every
relative path in `buf.gen.yaml` is therefore relative to `go/`. The Makefile is
the entry point that gets this right.

There are no BSR dependencies and no `buf.lock`. The only imports are well-known
types, which ship inside buf, so generation needs no network.

## Source disagreements

The .proto files were derived from three sources that disagree with each other:
`types/*.ts` (what the client declares), demo's Bun API (what currently works),
and infra's Go API and chaincode (the truest account of intended behaviour).
Every material disagreement is recorded as a `SOURCE CONFLICT:` comment at the
field or message it affects, with the resolution and why. Those comments are the
most useful thing in this directory; `grep -rn 'SOURCE CONFLICT' proto/` is a
reasonable way to read them.

Endpoints deliberately left out — `POST /lit-search`, the multipart branch of
`POST /paper/create`, sign-up's JWK, infra's Fabric debug routes — are recorded
the same way, at the place they would otherwise have gone.
